# دليل تشغيل TMDB والطوابير في NEXORA

> مرجع عملي للمرحلة الأولى من ترقية وحدة TMDB. يشرح ما تم تنفيذه، كيف يعمل، وكيف يتم تشغيله وصيانته لاحقًا.

## 1. نطاق هذه المرحلة

تم تنفيذ ثلاثة محاور رئيسية:

1. اختيار نتيجة TMDB يدويًا قبل اعتماد الإثراء.
2. إعدادات سياسة تحديث بيانات TMDB.
3. طابور تحديث قابل للإدارة مع عامل خلفي وإعادة محاولة.
4. تسجيل استهلاك TMDB وعرض ملخص يومي.

تم تأجيل البنود التالية عمدًا، ولا تعد جزءًا من هذه المرحلة:

- ربط حلقات TMDB بملفات الفيديو المحلية.
- نظام معرض الصور الكامل وجدول `media_assets`.
- مراجعة الأمان وتنظيف أسرار تاريخ Git.

## 2. المبدأ العام

المتصفح لا يتصل بـ TMDB مباشرة. جميع طلبات TMDB تمر عبر خادم Go، ثم تحفظ النتائج المهمة محليًا في PostgreSQL وملفات الصور المحلية حسب إعداد `ImageMode`.

تصفح الأعمال وصفحات السلاسل يتم من البيانات المحلية. لا يتم استدعاء TMDB عند التصفح العادي.

## 3. اختيار نتيجة TMDB يدويًا

### المشكلة التي يعالجها

البحث التلقائي قد يختار نتيجة خاطئة، خصوصًا في الحالات التالية:

- One Piece بين مسلسل وفيلم.
- الأنمي الذي له أفلام جانبية.
- الأعمال التي تحمل أسماء متشابهة.
- اختلاف الاسم العربي والإنجليزي.

### طريقة العمل

1. ينشئ المسؤول العمل أو يفتحه من لوحة إدارة الأعمال.
2. يحدد النوع: فيلم، مسلسل، أو أنمي.
3. يضغط `بحث في TMDB`.
4. يعرض النظام عدة مرشحين، وكل مرشح يحتوي:
   - العنوان.
   - العنوان الأصلي.
   - السنة.
   - التقييم.
   - الصورة.
   - رقم TMDB.
5. يختار المسؤول النتيجة الصحيحة.
6. يرسل النظام معرف TMDB المختار إلى الإثراء.
7. يجلب الخادم بيانات الإنجليزية والعربية لنفس المعرف، فلا يحدث بحث ثانٍ قد يختار عملًا مختلفًا.

### API

```text
GET /api/tmdb/candidates?title=One%20Piece&type=anime&year=1999
POST /api/media/:id/enrich?tmdb_id=12345
```

`tmdb_id` اختياري. عند عدم إرساله يعمل البحث التلقائي القديم، وعند إرساله يصبح المعرف معتمدًا يدويًا.

### الأنمي

- TMDB هو المصدر الأساسي للأنمي.
- يتم البحث في قسم TV لأن معظم الأنمي الطويل يسجل كمسلسل.
- يتم ترجيح النتائج اليابانية والنتائج المصنفة Animation.
- MAL يستخدم كـ fallback فقط عند عدم توفر نتيجة TMDB.
- لا يتم التعامل مع رقم MAL على أنه رقم TMDB.

## 4. إعدادات سياسة التحديث

تحفظ إعدادات التحديث في جدول `tmdb_settings` وتظهر في لوحة إعدادات TMDB.

| الإعداد | الوظيفة | الافتراضي |
|---|---|---:|
| `auto_refresh_enabled` | تشغيل أو إيقاف إنشاء المهام التلقائية | `false` |
| `refresh_interval_days` | عمر البيانات قبل إدخال العمل في التحديث الدوري | `30` يومًا |
| `refresh_on_open` | السماح بإضافة العمل المفتوح إلى الطابور إذا كان قديمًا | `false` |
| `refresh_stale_days` | عدد الأيام التي تجعل العمل المفتوح قديمًا | `7` أيام |
| `queue_max_concurrent` | عدد مهام الطابور المتزامنة | `1` |

### سياسة مقترحة

- مكتبة مستقرة: تحديث كل `30` يومًا.
- مكتبة تتغير باستمرار: تحديث كل `7` أيام.
- مسلسل يتابعه المستخدمون: فعّل `refresh_on_open`.
- مكتبة كبيرة قليلة الاستخدام: أبقِ التحديث التلقائي متوقفًا وشغّل تحديثًا يدويًا عند الحاجة.
- لا ترفع `queue_max_concurrent` فوق `4`.

### حفظ الإعدادات

يتم تعديل الإعدادات من صفحة TMDB ثم الضغط على `حفظ التغييرات`.

```text
GET /api/tmdb/settings
PUT /api/tmdb/settings
```

## 5. طابور تحديث TMDB

### جدول الطابور

Migration الطابور:

```text
server/migrations/0014_add_tmdb_refresh_queue.sql
```

الجدول هو `tmdb_refresh_queue`، ويحتوي على:

- `media_item_id`: العمل المطلوب تحديثه.
- `priority`: أولوية المهمة.
- `status`: حالة المهمة.
- `attempts`: عدد المحاولات.
- `last_error`: آخر خطأ.
- `scheduled_at`: موعد التنفيذ.
- `started_at`: وقت بدء التنفيذ.
- `finished_at`: وقت الانتهاء.
- `created_at`: وقت إنشاء المهمة.

### الحالات

| الحالة | المعنى |
|---|---|
| `pending` | تنتظر التنفيذ |
| `running` | قيد التنفيذ |
| `succeeded` | اكتملت بنجاح |
| `failed` | فشلت بعد استنفاد المحاولات |
| `cancelled` | أُلغيَت قبل التنفيذ |

### سلوك العامل الخلفي

- يعمل العامل كل `10` ثوانٍ.
- يحجز المهام باستخدام `FOR UPDATE SKIP LOCKED`.
- يرتب المهام حسب الأولوية ثم وقت الجدولة.
- عدد العمال يقرأ من `queue_max_concurrent`.
- الحد العملي الأعلى هو `4`.
- كل مهمة تنفذ نفس مسار إثراء العمل اليدوي.
- لا يسمح القيد الفريد بتكرار مهمة لنفس العمل في الحالة نفسها.

### إعادة المحاولة

- تتم إعادة المحاولة حتى `3` مرات.
- التأخير تصاعدي:
  - بعد المحاولة الأولى: دقيقة تقريبًا.
  - بعد المحاولة الثانية: دقيقتان تقريبًا.
  - بعد المحاولة الثالثة: تتحول المهمة إلى `failed`.
- يحفظ آخر رد خطأ في `last_error`.

### API الطابور

```text
GET  /api/tmdb/queue
POST /api/tmdb/queue
POST /api/tmdb/queue/:id/cancel
```

إضافة عمل إلى الطابور:

```json
{
  "media_item_id": 42,
  "priority": 10
}
```

## 6. متى تضاف المهام؟

### إضافة يدوية

من نموذج تعديل العمل في لوحة إدارة الأعمال، يضغط المسؤول `إضافة للطابور`.

### العمل المفتوح

إذا كانت الإعدادات التالية مفعلة:

```text
auto_refresh_enabled = true
refresh_on_open = true
```

عند فتح تفاصيل عمل قديم، تضاف له مهمة بأولوية أعلى، ولا ينتظر المستخدم انتهاء TMDB.

### التحديث الدوري

إذا كان:

```text
auto_refresh_enabled = true
```

يفحص العامل الأعمال الأقدم من `refresh_interval_days` ويدخل عددًا محدودًا منها إلى الطابور.

## 7. سجل الاستهلاك

يسجل النظام الطلبات في جدول:

```text
tmdb_usage_log
```

ويحفظ لكل سجل:

- نوع الطلب.
- endpoint.
- كود الاستجابة.
- حجم البيانات المنزلة.
- عدد الصور المنزلة.
- مدة الطلب.
- رسالة الخطأ.
- العمل المرتبط بالطلب عند توفره.
- وقت التنفيذ.

### الملخص الحالي

```text
GET /api/tmdb/stats
```

يعرض:

- إجمالي الطلبات.
- طلبات اليوم.
- طلبات الشهر الحالي.
- إجمالي البيانات المنزلة.
- بيانات اليوم.
- استهلاك اليوم بالميجابايت.
- نسبة استهلاك الحصة اليومية.
- إجمالي الصور.
- صور اليوم.
- الأعمال المثرية.
- الأعمال غير المثرية.
- آخر طلب.

### السجل اليومي

```text
GET /api/tmdb/usage/history?days=90
```

يعرض لكل يوم:

- التاريخ.
- عدد الطلبات.
- حجم البيانات بالميجابايت.
- عدد الصور.
- الطلبات الناجحة.
- الطلبات الفاشلة.

ويظهر هذا الجدول داخل لوحة إعدادات TMDB.

## 8. لوحة التحكم

تحتوي صفحة TMDB الآن على:

1. إعدادات أوضاع الجلب والصور.
2. وحدات البيانات القابلة للتفعيل.
3. فحص اتصال TMDB.
4. إعدادات أحجام الصور.
5. تحديث السلاسل القديمة.
6. سياسة التحديث والطابور.
7. قائمة مهام الطابور وحالاتها.
8. إلغاء المهام المنتظرة.
9. سجل الاستهلاك اليومي.
10. إحصائيات الاستهلاك العامة.

## 9. مسارات البيانات الرئيسية

### الإثراء اليدوي

```text
لوحة الإدارة
  → بحث مرشحي TMDB
  → اعتماد معرف TMDB
  → جلب en-US
  → جلب ar-SA بنفس المعرف
  → حفظ الحقول والـ snapshots
  → تحديث العلاقات والسلاسل عند الحاجة
```

### الطابور

```text
إضافة مهمة
  → pending
  → العامل يحجز المهمة
  → running
  → تنفيذ الإثراء
  → succeeded أو إعادة محاولة أو failed
```

### التصفح

```text
صفحة العميل
  → PostgreSQL / snapshots المحلية
  → لا اتصال مباشر بـ TMDB
```

## 10. Migrations المطلوبة

يجب تشغيل migrations بالترتيب، خصوصًا:

```text
0008_add_tmdb_settings.sql
0013_add_provider_collection_rating.sql
0014_add_tmdb_refresh_queue.sql
```

إذا كانت قاعدة البيانات موجودة قبل إضافة الحقول الجديدة، يجب تطبيق migration `0014` حتى تظهر إعدادات التحديث وجدول الطابور.

## 11. الاختبارات والتحقق

تم التحقق من:

- بناء الواجهة عبر `npm run build`.
- تجميع الخادم عبر `go build ./...`.
- اختبارات `internal/api` و`internal/db`.
- سلامة واجهة اختيار المرشحين وفحص المحرر.

قد توجد إخفاقات قديمة خارج نطاق هذه المرحلة في اختبارات metadata، خصوصًا الاختبارات التي تفترض تفعيل `reviews` وWatch Providers رغم اختلاف إعدادات الاختبار.

## 12. ما لم يكتمل في هذه المرحلة

هذه البنود محفوظة لخطة لاحقة ولا يجب تنفيذها ضمن هذا العمل:

1. ربط حلقات TMDB بملفات `video_files` بدرجة ثقة.
2. إنشاء `media_assets` لمعرض الصور والشعارات وصور الممثلين.
3. مراجعة الأمان وتنظيف أسرار Git.

## 13. الأعمال اللاحقة المقترحة داخل نطاق TMDB

هذه ليست ضرورية لتشغيل المرحلة الحالية، لكنها تحسينات مستقبلية لوحدة TMDB نفسها:

- إضافة صفحة تاريخ مفصلة حسب نوع الطلب والعمل.
- تصفية السجل بالتاريخ ونوع الطلب والحالة.
- تصدير CSV/JSON.
- زر إعادة المحاولة لمهمة فاشلة.
- زر إيقاف العامل وتشغيله من لوحة الإدارة.
- حد يومي فعلي يمنع بدء الطلب عند تجاوز الحصة.
- تسجيل كل طلب شبكي فرعي داخل `doGet` بدل تسجيل ملخص الإثراء فقط.
- Backoff خاص ومباشر لـ `429` مع قراءة `Retry-After`.
- تنظيف المهام القديمة الناجحة بعد مدة قابلة للتخصيص.
- إشعار المسؤول عند تراكم الفشل أو الاقتراب من الحصة.

## 14. قاعدة تشغيل مهمة

لا تستخدم التحديث الجماعي بلا حد. ابدأ دائمًا بعدد محدود، راقب سجل الاستهلاك، ثم زد العدد تدريجيًا.

الاختيار اليدوي مهم للأعمال الملتبسة، والطابور مهم للمكتبات الكبيرة، وTTL مهم لمنع تكرار الطلبات بلا فائدة.
