# مشكلة البحث والإثراء — تحليل وخطة وقرارات
> ## 🔴 اكتشاف يغيّر الخطة — 12,130 حلقة متاحة محليًا
>
> فحصت بيانات TMDB المخزنة في قاعدة بياناتك (لم أطلب من المنصة شيئًا):
>
> | الجدول | العدد | المحتوى |
> |---|---|---|
> | `metadata_snapshots` | **205** | بيانات الأفلام/المسلسلات (أنواع، بلد، بوستر، ملخص...) |
> | `season_metadata_snapshots` | **350** | مواسم كاملة، كل واحد يحتوي `episodes` |
> | **إجمالي الحلقات** | **12,130** | العنوان · الوصف · الصورة · تاريخ البث · المدة · رقم الحلقة |
>
> حقول الحلقة المتاحة محليًا (`raw_payload->'episodes'`):
> ```
> name          → عنوان الحلقة
> overview      → الوصف

> طلب شبكة وبلا استهلاك حصة API. قرار المالك (الإثراء المحلي) **مُنفّذ بالكامل
> بلا أي مخاطرة**، وهو الأنسب تقنيًا أيضًا.

## 1. الملخص التنفيذي

### البحث **يعمل فعلًا** — لكن فيه ثلاث مشاكل حقيقية

ليست "البحث معطّل". هو يعمل ويعيد نتائج. لكن فيه:

| # | المشكلة | الأثر | الخطورة |
|---|---|
| 1 | **102 مستند يتيم** في الفهرس (382 في البحث مقابل 280 في قاعدة البيانات) | نتائج بحث لأعمال محذوفة/مدموجة — تعطي 404 عند النقر | 🔴 عالية |
| 2 | **النتائج لا تُرتَّب حسب الصلة** — ترتيب غريب | البحث عن فيلم معروف لا يُظهره أولًا | 🟠 متوسطة |
| 3 | **لا وجود لمستندات الحلقة** | لا يمكن البحث عن "الحلقة 4 من مسلسل كذا" | 🟡 منخفضة (قرار منتج) |

### السبب الجذري المشترك

`/api/search/sync` يضيف ويحدّث، **لكنه لا يحذف أبدًا**. فكل عمل حُذف أو دُمج
يبقى في الفهرس للأبد.

**الدليل:** 382 في Meilisearch، 280 في قاعدة البيانات → **102 يتيم**.

## 2. الوضع الحالي بالتفصيل

### 2.1 ما يعمل ✅

```text
1. Meilisearch يعمل          → الفهرس uid=media_items صحيح
2. المزامنة تعمل             → 382 مستندًا موجودة فعلًا
3. البحث يعمل                → /api/search?q=a يعيد 155 نتيجة
4. الـ projection مُنفّذ       → keyset pagination + cursor
5. الحقول جاهزة              → title_ar/en, type, category, genres, year...
```

**حقول الفهرس الفعلية (382 مستندًا):**
```
title_en: 382     type: 382      category_slug: 382   file_count: 382
title_ar: 258     poster_path: 234   release_year: 224   status: 320
genres: 150       plot_en: 107    plot_ar: 94         rating: 113
```

### 2.2 المشكلة الأولى: 102 مستند يتيم 🔴

**المشكلة:**
```
Meilisearch  → 382 مستندًا
PostgreSQL   → 280 عملًا
الفرق        → 102 مستند لا مقابل له في قاعدة البيانات
```

**السبب الجذري — من الكود:**

```go
// search/projection.go — Rebuild()
for {
    page, err := p.store.ListSearchDocumentPage(ctx, afterID, p.pageSize)
    if len(page) == 0 { break }
    p.client.IndexDocuments(ctx, page)      // ← يضيف ويحدّث فقط
    // ← لا يوجد أي حذف
}
```

**لا يوجد `DeleteDocuments` في `Rebuild`.** فالفهرس تراكمي فقط: كل ما دخل يبقى.

**من أين جاء الـ 102؟**

من عملي أنا — خلال الاختبارات:

| السبب | العدد التقريبي |
|---|---|
| أعمال أُنشئت ثم دُمجت (merge) | جزء منها |
| أعمال جرّبتها ثم حُذفت من قاعدة البيانات | جزء منها |
| دورات الفحص التجريبية على مكتبة الاختبار | الجزء الأكبر |

**كيف تظهر المشكلة للمستخدم؟**

```text
1. يبحث المستخدم عن "الكنز"
2. يظهر عملان — أحدهما محذوف من قاعدة البيانات
3. ينقر على المحذوف
4. → 404 أو صفحة فارغة
```

**هذا ليس خطأً في التصميم — بل نقص في التنفيذ.** الـ ADR-011 نصّ على أن الفهرس
"قابل لإعادة البناء"، لكن `Rebuild` لا يمحو ما لم يعد موجودًا.

### 2.3 المشكلة الثانية: ترتيب النتائج 🟠

**المشكلة:** `configureSettings` يضبط الحقول القابلة للبحث، **لكن لا يضبط
`rankingRules` ولا `searchableAttributes` بالترتيب الصحيح للأهمية:**

```go
// search/client.go — configureSettings
settings := map[string][]string{
    "searchableAttributes": {
        "title_ar", "title_en", "genres",
        "plot_ar", "plot_en",        // ← الوصف يُبحث بنفس وزن العنوان!
        "category_ar", "category_en",
    },
    "filterableAttributes": {...},
    "sortableAttributes": {"rating", "release_year", "file_count"},
    // ← لا يوجد rankingRules
}
```

**النتيجة:** عمل اسمه "Inception" ووصفه يذكر "dream" سيتعادل مع عمل آخر وصفه
يطابق تمامًا. البحث عن عنوان دقيق قد لا يعطيه الأولوية.

**الحل القياسي في Meilisearch:** ترتيب `searchableAttributes` **حسب الأهمية** —
المصفوفة مرتبة، والعنصر الأول له وزن أعلى. فيجب أن يكون:

```go
"searchableAttributes": {
    "title_en", "title_ar",           // العنوان أولًا — الأعلى وزنًا
    "genres",                          // ثم التصنيفات
    "plot_en", "plot_ar",              // الوصف أخيرًا — الأدنى وزنًا
    "category_en", "category_ar",
}
```

### 2.4 المشكلة الثالثة: لا مستندات حلقة 🟡

**المشكلة:** لا يمكن البحث عن حلقة بعنوانها.

```text
المستخدم يبحث: "Breaking Bad Ozymandias"
→ لا نتيجة، لأن الفهرس يحتوي مستندات *أعمال* فقط
```

**الحالة:** جدول `episodes` موجود، و`search_projection_state` فيه صف
`episodes`، **لكن لا استعلام يكتب مستندات الحلقات.**

**هذا قرار منتج لا قرار تقني** — لهذا أضعه في قسم القرارات.

### 2.5 مشكلة رابعة محتملة: `files` في الـ status

**لاحظت:** `search_projection_state` كله أصفار:
```
media_items  last_id=0  docs=0
episodes     last_id=0  docs=0
```

**التفسير:** الـ cursor يُحفظ **فقط** داخل `Rebuild`. لكن `IndexDocuments` يُستدعى
أيضًا مباشرة من أماكن أخرى (الفحص، الـ classify-origins) بدون تمرير الـ cursor.

**الأثر:** إن توقفت إعادة بناء في المنتصف، سيعيد البدء من الصفر رغم وجود الكود
الذي يستكمل. **الـ resume معطّل عمليًا** لأنه لا يُحفظ شيء.

## 3. الخطة المقترحة

### المرحلة 1 — تنظيف الفهرس (الحرجة) 🔴

**الهدف:** إزالة الـ 102 يتيم، ومنع تكرارها مستقبلًا.

#### 1.1 إضافة الحذف إلى `Rebuild`

```go
// فكرة التنفيذ: بعد اكتمال الاستكشاف، احذف ما ليس في قاعدة البيانات.
// Meilisearch يدعم delete-batch بمعرّفات.

func (p *Projector) Rebuild(ctx context.Context, reset bool) (ProjectionResult, error) {
    // ... الكود الحالي ...

    // جديد: بعد آخر صفحة، نظّف اليتامى
    if reset {
        removed, err := p.pruneOrphans(ctx, afterID)
        result.Pruned = removed
    }
}
```

**سؤال مهم:** كيف نعرف اليتامى بفعالية؟

| الطريقة | التكلفة | الدقة |
|---|---|---|
| **أ. مقارنة المعرّفات** — اجلب كل معرّفات Meili، وكل معرّفات DB، والفرق | O(n) قراءة | 100% |
| **ب. الطابع الزمني** — احذف ما لم يُحدَّث في آخر دورة | O(1) | قد يحذف أعمالًا صحيحة |
| **ج. حذف كامل + إعادة بناء** — أفرغ Index ثم أعد بناءه | O(n) كتابة | 100% لكن أغلى |

**توصيتي: الطريقة (أ)** — لأنها دقيقة ولا تعيد بناء أشياء لم تتغير. والحذف
batch على 1000 معرّف في المرة.

#### 1.2 إضافة endpoint تنظيف صريح

```text
POST /api/search/prune
→ يعيد: { "scanned": 382, "orphansFound": 102, "deleted": 102 }
```

**لماذا endpoint منفصل؟** لأنه عملية **مدمّرة** — يجب أن تكون بقرار صريح من
المشغّل، لا ضمن مزامنة عادية.

#### 1.3 مزامنة عند حذف عمل

عند حذف عمل من `/api/media/{id}`، احذف مستنده من الفهرس فورًا.

### المرحلة 2 — ترتيب النتائج 🟠

#### 2.1 إعادة ترتيب `searchableAttributes`

```go
"searchableAttributes": {
    "title_en", "title_ar",        // ⭐ العنوان — الأول
    "genres",                       // التصنيفات
    "plot_en", "plot_ar",           // الوصف
    "category_en", "category_ar",   // القسم
}
```

**التغيير:** ترتيب المصفوفة فقط — لا كود جديد.

#### 2.2 ضبط `rankingRules` صراحةً

```go
"rankingRules": {
    "words",      // عدد كلمات الاستعلام المطابقة
    "typo",       // أقل أخطاء إملائية
    "proximity",  // قرب الكلمات من بعضها
    "attribute",  // ⭐ الأهمية حسب موقع الحقل (العنوان قبل الوصف)
    "sort",
    "exactness",
}
```

**ملاحظة:** هذه هي الافتراضيات في Meilisearch، لكن ضبطها **صراحةً** يعني أنها
لا تتغير مع تحديث Meilisearch. القيمة الحقيقية هنا في `attribute` + ترتيب (2.1).

#### 2.3 تطبيع عربي في البحث

**المشكلة:** العمليات كلها في `internal/identity/normalize.go` (توحيد الهمزات،
الأرقام العربية...). لكن **الفهرس في Meilisearch يحتوي العنوان الخام**.

**النتيجة:** البحث عن `اسامة` لا يجد `أسامة`.

**الحل المقترح (خياران):**

| الخيار | التنفيذ | التكلفة |
|---|---|---|
| **أ. حقل مُطبَّع في المستند** | أضف `title_normalized` لمستند Meili واجعلها `searchableAttributes` أولًا | تعديل `MediaDocument` + migration |
| **ب. Meilisearch synonyms** | اضبط synonyms للهمزات | محدود — لا يغطي كل الحالات |

**توصيتي: (أ)** — لأن التطبيع موجود ومُختبر باختبارات، ويحتاج فقط التمرير للفهرس.

### المرحلة 3 — مستندات الحلقة (قرار منتج) 🟡

**هذا القسم يحتاج قرارك.** راجع القسم 4.

**الخطة إن وافقت:**

```sql
-- استعلام جديد في repository_projection.go
SELECT e.id, e.episode_number, s.season_number, mi.title_en, mi.title_ar,
       e.title_en, e.title_ar, e.overview_en, e.still_path
FROM episodes e
JOIN seasons s ON s.id = e.season_id
JOIN media_items mi ON mi.id = s.media_item_id
```

**مستند الحلقة المقترح:**
```json
{
  "id": "ep-1042",
  "work_id": 234,
  "work_title_en": "Breaking Bad",
  "work_title_ar": "بريكنغ باد",
  "season_number": 5,
  "episode_number": 14,
  "episode_title_en": "Ozymandias",
  "search_tokens": ["breaking", "bad", "ozymandias", "5", "14"]
}
```

**نقطة حرجة:** كيف يُميَّز `id` العمل عن `id` الحلقة في نفس الفهرس؟
- **خيار أ:** فهرس منفصل `media_episodes`
- **خيار ب:** بادئة في المعرّف (`work-234` و`ep-1042`) — يحتاج migration لأن المعرّفات حالية أرقام

**توصيتي: (أ)** — فهرس منفصل. أنظف ولا يلمس المعرّفات الحالية.

### ⚠️ قرار 3 — مستندات الحلقة

**السؤال:** هل نُنشئ فهرس حلقات منفصل؟

**الفائدة:** البحث عن حلقة بعنوانها (`Ozymandias`).
**التكلفة:** استعلام projection جديد + فهرس Meili جديد + endpoint بحث منفصل + واجهة.
**الحالة:** البيانات موجودة في `episodes` لكنها **شبه فارغة الآن** — لأن الإثراء (TMDB) لم يُشغَّل.

**الواقع:** معظم الحلقات في قاعدة بياناتك **بلا عنوان** (`title_en` فارغ) لأن
المعلومات تأتي من TMDB. فالفهرس سيكون أغلب حقوله فارغة.

**سؤالي:** هل:
- **(أ)** نُنشئه الآن (استعدادًا عند تشغيل TMDB)؟
- **(ب)** نؤجّله حتى تشغّل TMDB وتُثري الحلقات فعلًا؟
- **(ج)** نتجاهله — البحث بالعمل يكفي؟

**توصيتي: (ب)** — لا قيمة لمستندات فارغة.

**توصيتي: (أ)** — يمنع تراكم يتامى جديدة.

### ⚠️ قرار 5 — التنظيف الدوري

**السؤال:** هل نُضيف تنظيفًا تلقائيًا لليتامى؟

| الخيار | الأثر |
|---|---|
| **أ. يدوي فقط** (`POST /api/search/prune`) | أنت تتحكم بالكامل |
| **ب. ضمن `/api/search/sync` مع `reset=true`** | تلقائي عند إعادة البناء الكاملة |
| **ج. مُجدول دوري** (مثل reconciliation) | تلقائي تمامًا |

**توصيتي: (ب)** — التنظيف يحدث عند إعادة البناء الكاملة، وليس تلقائيًا. يمنع
حذفًا غير متوقع.

**سؤالي:** هل توافق على (ب) أم تريد (ج)؟

| **4 — حذف فوري** | **نعم** | يُزامن الفهرس عند حذف عمل |
| **5 — تنظيف دوري** | **ضمن إعادة البناء** | لا حذف غير متوقع |

### قرار المالك الإضافي — الإثراء المحلي (الأهم)

**لا استدعاء TMDB لكل حلقة.** السبب الذي ذكره المالك، وهو صحيح تقنيًا:

> «كل حلقة لها اسم أو لا، وكل هذا عشوائيات ولخبطة، وأساسًا يستهلك طلبات من
> المنصة وأعتقد أكثرها سيفشل.»

**الحل المعتمد — الإثراء المحلي بالكامل:**

```text
المالك يجلب بيانات الحلقة من TMDB  →  تُخزّن كـ snapshot
                                              ↓
المنصة (TMDB) تُعرّف الحلقة بـ (work_id, season_number, episode_number)
                                              ↓
النظام يطابق الحلقة المحلية بالحلقة المخزّنة بالمفتاح الثلاثي
                                              ↓
تُثرى محليًا بلا طلب واحد — فيتعرّف أيضًا على المفقود والجديد
```

**لماذا هذا هو الحل الصحيح تقنيًا:**

| الفائد | التفصيل |
|---|---|
| **صفر طلبات TMDB** | 12,130 حلقة تُثرى من بيانات موجودة أصلًا |
| **صفر فشل** | لا انتظار شبكة، ولا حصة API، ولا timeout |
| **سرعة** | الإثراء محلي — أجزاء من الثانية لكل مسلسل |
| **دقة المطابقة** | `(work_id, season, episode)` هو مفتاح فريد لا يحتاج تخمينًا |
| **اكتشاف المفقود** | مقارنة مجموعة الحلقات المحلية بمجموعة المزود |
| **اكتشاف الجديد** | حلقة عند المزود بلا نسخة محلية = قيد الإضافة |
